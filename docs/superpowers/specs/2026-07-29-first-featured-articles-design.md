# Hub 首批代表文章内容设计

## 目标

为 Hub 增加三篇能够代表作者当前观点、真实经历与实践方法的文章：

1. AI 时代的编程与认知主权；
2. ORRA 自我改进方法的两个月实践；
3. Codex 参与 Git 操作时的一次真实事故复盘。

个人网站不是博客园的完整镜像。这三篇文章应形成一个小型精选集，分别回答：

- AI 可以完成越来越多工作以后，人的能力如何继续形成；
- 一套方法怎样通过真实生活事件反复验证和调整；
- 使用 Coding Agent 时，怎样把关键操作的方向盘留在人手中。

## 已确认的内容方向

用户已经确认首批实现上一轮推荐的第一梯队三篇文章。

采用“精选和重写”的方式：

- 保留第一人称、真实事件和未完全解决的问题；
- 修正错别字、标点和明显重复；
- 不把文章改写成通用 AI 教程或标准答案；
- 不为了显得完整而补充作者没有经历过的事实；
- 三篇文章都使用现有 Markdown 内容系统，不引入新的元数据或图片。

不采用以下方式：

- 直接复制整个 Notion 对话记录；
- 批量搬运博客园归档；
- 把 ORRA 写成只有定义、没有失败案例的抽象方法论；
- 为三篇文章额外添加标签、分类、来源地址等元数据。

## 文章一：在 AI 时代，关于编程的思考

### 定位

这是首批文章中的核心立场文章。它不是讨论“AI 会不会取代程序员”，而是讨论：

> 当 AI 能够完成需求分析、编码、调试、验证和发布时，人如何避免把人机系统的成果误认为自己的能力。

### 主要来源

- Notion 主文章《在 AI 时代，关于编程的思考》；
- 主文章下的两份完整讨论记录只用于核对思想演化和避免遗漏，不直接大段搬入正文。

### 编辑原则

- 最大限度保留现有手写正文的结构和判断；
- 保留《长征》人物、做菜、中位数与 P90、TDC PPT 与 QA 四个类比；
- 保留对 AI 初始建议的逐项推翻，因为这是文章最独特的思考过程；
- 将“阶段性结论”明确写成阶段性，而不是包装成最终答案；
- 将用词统一为“认知升级”“认知闭环”“结果可验证任务”“能力生成任务”；
- 修正错别字和病句，但不把表达抛光成没有个人痕迹的学术文章。

### 结构

1. 问题从哪里开始；
2. 四个真实类比揭示的能力倒挂；
3. AI 给出的常见建议；
4. 为什么这些建议仍然不够；
5. 工作完成与能力成长已经分离；
6. 当前的阶段性结论；
7. 接下来准备怎样实践；
8. 仍然没有解决的问题。

### 摘要

> AI 可以直接生成优秀的代码、材料和答案，但不会自动把产生这些结果的能力留在人身上。这是我在一次真实失败之后，对编程、学习与认知主权的阶段性思考。

## 文章二：把自己当作一个长期成长系统

### 定位

这是 ORRA 的真实实践记录，不是自律建议，也不是健康方法科普。

ORRA 表示：

```text
Observe → Record → Review → Adjust
观察 → 记录 → 复盘 → 调整
```

文章通过数月内真实发生的戒烟、饮食和情绪事件，说明规则如何从一次次成功与偏航中形成。

### 主要来源

- 《把自己当作一个长期成长系统》；
- 《回家假期全程没有抽烟》；
- 《晚上强烈想吃汉堡炸鸡时，用健康食物先垫餐刹车》；
- 《每餐都清楚热量，但附加食物不断叠加导致全天超标》；
- 《TDC 未通过后的情绪顶峰中守住基本盘》；
- 《事上练，正是修行时》只用于提炼“真实场景才是练习场”的主线。

### 编辑原则

- 同时保留“赢了一次”和“基本盘偏航”，避免把 ORRA 写成成功学；
- 使用具体事件，但删除与方法无关、可能喧宾夺主的私人关系细节；
- 不把体重、戒烟或饮食经验写成医学建议；
- 明确 AI 在方法中的位置：帮助整理记录和提供交叉视角，但观察、行动与调整仍由本人承担；
- 强调调整规则应越来越简单，而不是越来越复杂。

### 结构

1. 为什么需要 ORRA；
2. ORRA 四个步骤分别做什么；
3. 案例一：旧场景中没有重新抽烟；
4. 案例二：先垫健康食物，为冲动刹车；
5. 案例三：知道所有热量仍然超标；
6. 案例四：重大失败后守住基本盘；
7. 从复杂控制转向简单规则；
8. AI 能帮助什么，不能替代什么；
9. 当前边界与下一阶段。

### 摘要

> ORRA 是我给自己总结的一套长期改进方法：观察、记录、复盘、调整。它不是要求每天完美，而是把成功、偏航和情绪顶峰都变成下一次可以使用的经验。

## 文章三：一次错误的 Git Tracking

### 定位

这是一次已经发生的真实事故复盘。重点不是讲解 `git worktree add`，而是说明：

> Coding Agent 可以提高执行速度，但分支、远端和历史这类高影响操作必须由人确认。

### 主要来源

- Notion 与博客园已有文章《使用 Codex 的一次危险提醒》。

### 编辑原则

- 保留错误分支关系、发现过程、影响范围和后续规则；
- 区分“基于 `main` 创建”与“tracking `origin/main`”；
- 避免把特定 Git 配置下的行为写成所有环境都会自动发生；
- 将旧文中的 `master` 统一为当前项目使用的 `main`，同时说明事故发生时目标是主分支；
- 把重复感慨压缩成可复用的检查清单；
- 保留“AI 可以踩油门，但方向盘必须在人手里”作为结尾。

### 结构

1. 一条被忽略的 tracking 提示；
2. 基于主分支与 tracking 主分支不是一回事；
3. 问题怎样进入远端历史；
4. 为什么不能轻易回滚；
5. 真正的问题不是 Git 命令；
6. 创建任务前后的检查清单；
7. 哪些操作必须停下来人工确认。

### 摘要

> 一次错误的分支 tracking，让功能分支提交绕过正常合并流程进入了主分支。真正危险的不是某条 Git 命令，而是我默认工具流程会自己正确。

## 内容质量要求

三篇文章都必须满足：

- 第一个一级标题是文章标题；
- 标题后的第一个引用块是摘要；
- 不包含 Front Matter；
- 不包含原始 HTML；
- 不包含 Notion 临时签名图片地址；
- 不虚构事实、数据、时间或结果；
- 每篇正文能够独立阅读，不依赖读者访问 Notion 或博客园；
- 文章之间可以共享“方向盘”“基本盘”“认知主权”等词，但不能重复大段论证。
